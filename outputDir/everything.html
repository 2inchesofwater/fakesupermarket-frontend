Feeback from 2026-02-09
Some DOM changes to the Button component -

  • - Inside the DOM, the button's icon and label have been wrapped inside a span element.
    -- It's do with accessibility. Most often, we'll want to apply the 'aria-hidden' attribute to icons, and not directly into the SVG itself.
    -- Introducing the spans now is a minor change; it will future-proof us against vastly more costly overhauls for things like more-complicated accessibility situations and/or internationalisation.
    -- Inspect the Primary Default w Text button and the Primary Default w Icon + Text button; I've manually updated those with the span elements.
  • - The Android icon used in the Storybook introduced an unforeseen weirdsie. You see, that particular file uses both Fill and Stroke to style its colours. And that's why the original Android robots from Storybook now look broken...
    - SVG files used elsewhere throughout the site completely freak out if they're styled with both Fill and Stroke.
    -- Update: I've updated the Android icon across all instances to only use a `fill` property.
  • - Small and Large buttons have been introduced as exemplars for Storybook.
  • - Clarified the role of Primary, Secondary, and Tertiary button variants.
  • - An exemplar of the Disabled state has been introduced.
    I believe (but could be mistaken) that only Primary buttons would ever receive the disabled state; that's because we should only ever need to prevent a user from committing to a primary action.
  • - An icon-only Primary button cannot ever exist, and has been nuked.

Feedback for 2026-05-16

  • Long story short, the syntax of .fs-dialogue-sm and .fs-dialogue-inline became too muddy, especially with the Onboarding and Interview overlays looming. So in the CSS, I've cleaved off each of these dialogue blocks to be their own thing.
  • While each component is now its own thing, I target the class names (not the ID property). This is because End Early and Checkout - No Need both appear multiple times on the same page.
  • To that end, meet .fs-dialogue.fs-taskReminder, .fs-dialogue.fs-endEarly, .fs-dialogue.fs-infoCheckoutNoNeed, and .fs-dialogue.fs-infoCheckoutPostscript.
  • Note: I haven't been through the other instances of the FS Dialogue boxes which were copied over from Storybook yet. They're still using the old class names.
  • Looking forward: During early UX tests, people are doing well with "put things in cart". They're not doing well with "go through the checkout". I'd be keen to add some interactivity to End Early, so that if you've added something to your cart, you'll instead get a prompt to go through the Checkout (or back to your 'shopping list').

Feedback for 2026-05-13

  • Very small HTML changes to these Dialogue components thus far; but probably more to come. I don't think I have a good grasp on my own taxonomy / class names. Like, I think the separation between Dialogue and End Early components reflects that the taxonomy isn't right (on my part). It gets even worse when we consider that the Onboarding and Interview panels also use the .fs-dialogue styles.
  • I also want to run some colour-contrast tests and implement colour changes.
  • Recommendation: Update these as late as practical, and/or let's figure out a plan.

Logo as a SVG symbol

Added to HTML

Inspect the DOM for this explanation to make sense. There are three parts to this -

  • The use element which instantiates the SVG symbol so it can be used as an image. It can appear multiple times per page.
  • The symbol itself. It must appear once per page, typically at the far end of the page.
  • The defs piece – it defines the linear gradient inside the logo. It must also appear once per page, typically at the far end of the page.

ELI5? The defined linear gradient is referenced by an 'id' property. If a SVG file is simply rendered directly into a page more than once, those id properties will clash because they're unable to be scoped. You end up with the linear-gradient being a flat, incorrect colour.
